## 冲突及适配

内容审核服务出现三处文本冲突，均保留双方字段和配置：

1. 请求同时保留二开的 `AuditEventID` 和官方的 `riskControlLogOnly`。
2. 运行时快照同时保留渠道配置 `v2` 和白名单 `allowlistedUsers`。
3. 设置读取同时包含 `SettingKeyContentModerationV2` 和 `SettingKeyCyberPolicyUserAllowlist`。

审核仓库与管理路由自动合并，保留官方白名单计数排除和新 Claude 查询路由，也保留二开审核账本及管理接口。官方 v0.2.10 本次差异不含数据库迁移，二开现有迁移原样保留。

### 白名单与多渠道审核的业务适配

官方白名单语义为继续保留审计证据，同时豁免本地拒绝、自动处罚和通知。只依赖原 `Check` 返回时的豁免，会让二开同步审核的统计仍记成拦截或错误，也可能留下 503 错误码。

在 `checkModerationV2` 中，于记录和统计之前应用请求准入时捕获的白名单状态：

- 保留命中分数、原因、渠道、调用轨迹和账本费用。
- 将网关决策设为允许，清除拦截状态、消息、HTTP 状态及错误码。
- 日志使用官方 `risk_control_log_only` 模式，沿用官方的处罚与哈希副作用保护。
- 同步统计按允许计数，避免把白名单请求记为拦截。
- 兼容与强审模式均沿用原预算；预算耗尽时白名单豁免本地拒绝，但不会增加模型调用。
- 异步任务保留准入快照；移出白名单后的新请求重新执行正常拦截，即使复用先前审核判定缓存。

本机缺少 Go 和 Docker，后端与数据库集成验证使用仓库配置的 GitHub Actions 环境（Go 1.27.0），结果以升级 PR 和对应 CI 记录为准。只有所有检查通过后才更新远端 main。

程序回归不代表真实审核模型的准确率和延迟已验证；本次没有运营商审核 Key，也没有连接线上数据库。部署后的规则质量仍需通过实际业务样本和后台试跑确认。
